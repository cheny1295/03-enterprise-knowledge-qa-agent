# 04 AI 辅助使用、个人贡献与验证

## 1. 使用范围

本项目采用“人定边界、AI 加速实现、证据回查”的协作方式。AI 用于架构草拟、
代码草拟、局部实现、测试补充和文档整理；提交者主导需求范围、分层要求、审查方向
和交付安排，具体接口方案由 AI 辅助细化。AI 产出不直接视为事实或验收结果，
结论以代码、测试和运行材料为准。

## 2. 协作分工与投入

- 提交者根据题目要求确定核心范围，明确向量数据库、意图识别、多租户隔离、浅层
  快答、深层查询和兜底回复属于必须覆盖的架构能力。
- 提交者要求先做分层设计和资料补足，随后依次实现、补齐最小示例、对照要求并迁移
  交付；契约与模块的具体实现顺序由 AI 辅助安排。
- AI 编码代理依据已确认的架构补写领域对象、运行循环、适配器、CLI、合成资料和
  局部测试，并通过本机命令生成运行材料。
- `Search → Read → Evidence → Citation`、可信身份、租户过滤、预算约束和错误状态
  均以代码或输出材料核对，不以 AI 说明替代验收。
- 实际投入时间：约 5 小时，由提交者确认。
- 本记录不声称提交者逐行编写了 AI 生成的每一行代码；个人贡献重点记录为需求判断、
  架构决策、边界审查、优先级控制和交付验收。
- 向量库、CUDA 和 provider 的真实运行仍为 `runtime_evidence_pending`。

## 3. 个人贡献：从需求到交付的决策责任

在当前证据范围内，可以明确归入提交者的贡献包括：

### 3.1 需求定界与优先级

- 选择企业知识问答 Agent 作为题目，将“能解释、能运行、能回查”作为首版目标；
- 明确提出向量数据库、意图识别、多租户隔离、浅层快答、深层查询和兜底回复必须覆盖，
  避免实现只停留在单一检索问答路径；
- 明确采用逐步实现和有限测试的推进方式，将“缺少真实数据和可用模型”作为当前验证约束；
- 要求按 `要求.md` 制作最小 example 并核对完成度，使代码、示例与提交规范建立对应关系。

### 3.2 架构与工程决策

- 提出“每一层、每个状态、每个工具都要详细设计”，推动架构从概念分层落实到职责、
  接口、进入退出条件和失败处理；
- 要求依据需求与参考资料开展独立子 agent 审查，并在审查后形成修复文档、继续修复，
  而不是把首版架构直接当成最终方案；
- 要求以问题覆盖为指标递归补充资料，使检索、证据、权限和运行边界都有明确讨论；
- 在上述要求下，AI 辅助细化出六层职责、`SearchCandidate → ReadEvidence → Claim/Citation`
  证据链、状态/错误分离、可信租户上下文、工具白名单和双预算。具体字段与接口属于
  协作产出，不表述为提交者独立手写设计。

### 3.3 质量标准与交付组织

- 持续追问“功能是否完成”“除了真实验证还有哪些未完成”，促使交付结论区分设计、
  本地实现和真实运行证据；
- 要求按考核规范覆盖正常、冲突、资料外、改写、上下文追问和工具失败场景；由 AI
  辅助实现入口、测试及 Trace 留存；
- 明确提出先优化工作区文档，再迁移至提交区，并记录实际用时约 5 小时；
- 迁移后由 AI 编码代理实际运行六场景和三项聚焦测试，作为可核对的交付材料。

运行命令的执行与输出读取由 AI 编码代理通过本机工具完成，本记录不声称提交者已亲自
执行全部测试或逐行编写全部实现；提交者对需求、架构、边界和最终交付内容承担审阅
与确认责任。

## 4. 真实验证边界

本次最小 example 复用了已形成的核心契约，补齐 CLI 场景入口、自动材料写出、3 项
聚焦测试和交付说明；提交区已实际执行六类场景，并保存对应输入、输出、Trace 和
测试结果。该结果证明的是离线流程可复现，不是生产系统效果。

本轮未调用外部业务 LLM，不下载模型，不提交真实密钥，不使用真实员工资料，也没有
把模型内部 reasoning 写入 Trace。离线 `OfflineModel` 只验证结构化动作循环和错误映射，
不证明真实模型的决策质量。
