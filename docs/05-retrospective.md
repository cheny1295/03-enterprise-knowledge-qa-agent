# 05 复盘、学习收获与下一步

## 1. 实际投入

本项目本阶段实际投入约 **5 小时**，优先完成可运行的核心链路和可审查材料，没有将
界面、部署、多 Agent 或生产 Runtime 纳入本次范围。

## 2. 项目完成度与个人评价

在约 5 小时内，本项目完成了一个可复查的离线首版：从可信身份、快照绑定、意图路由、
Search/Read、冲突分析、模型动作循环到统一结果校验，形成了完整的结构化闭环。
`examples/` 同时保存明确答案、资料冲突、资料不足、上下文追问和工具失败路径。

对本次个人表现的评价是：**在有限时间内较好地完成了需求主导、问题追踪和交付组织，
能够通过明确设计要求与多轮审查，把单点问答推进为具有权限、证据和运行边界的系统方案。**
优势在于不满足于“功能清单上写了有”，而是持续要求说明每层、每个状态、每个工具的
责任，并将发现的问题落实到修复文档。

| 个人能力 | 本次体现 | 需要继续加强 |
|---|---|---|
| 业务理解 | 明确浅层快答、深层查询和兜底都要覆盖，兼顾效率与可靠性 | 用真实用户问题验证路由质量 |
| 系统性设计 | 主动补充向量库、意图识别、多租户，要求逐层/逐状态/逐工具细化 | 深入真实后端的一致性与失败恢复 |
| 学习与改进 | 要求按问题覆盖查资料，通过独立审查和修复不断收敛方案 | 更早停止外围调研，把时间留给真实模型验证 |
| 交付意识 | 制作最小示例、核对要求、先整理文档再迁移 | 提交前亲自复现关键路径并完成仓库提交 |

这些评价针对本次需求与交付工作，不等同于独立完成全部代码、生产级经验或真实模型
效果已达标。具体 AI 辅助范围见 [AI 使用与个人贡献](04-ai-usage.md)。

## 3. 已完成的最小闭环

- 可信身份与租户上下文先于知识访问；
- 意图路由区分快答、深层查询和兜底；
- Search 只产生候选，Read 才产生可引用证据；
- 模型依据 Observation 选择下一动作；
- 冲突、资料不足、工具失败和预算耗尽分别返回；
- 最终结果统一回查引用并输出 Trace。

## 4. 最难的问题与解决方式

1. **区分检索候选和可引用证据**：候选只能驱动 Read，不能直接进入最终引用。
2. **处理冲突而不猜优先级**：同主题不同规则必须保留双方 Evidence，除非资料显式
   给出范围、时间或优先级关系。
3. **保证失败语义真实**：provider、向量库、读取错误和预算耗尽不能统一改写为
   `insufficient_evidence`。
4. **在没有真实模型时保留动态决策形状**：Mock 必须依据 Observation 选择下一动作，
   而不是只记录固定脚本。

## 5. 当前限制

本次最小 example 选择复用核心而非复制一套问答框架，以减少评审所需入口。
输入、实际输出和 Trace 现在由同一次运行自动写出，避免手工材料与新请求不对应。
这改善了运行材料可复查性，但不能替代真实模型决策与检索效果验证。

- 尚无真实 embedding 权重和 CUDA 运行证据；
- 尚无 Qdrant local 实际写入、查询、删除证据；
- 尚无外部 provider 请求证据；
- 合成资料规模小，不能据此评价召回质量、意图准确率或生产性能；
- 管理摄取接口已有契约边界，但未作为本阶段的完整发布验收。

## 6. 学习收获

- 事实答案必须从可回查 Evidence 生成，检索候选不能直接作为引用；
- 冲突处理的关键不是猜一个“最新”规则，而是保留双方并请求缺失条件；
- 工具失败、资料不足和预算耗尽需要不同状态，便于用户和评审判断；
- 在没有真实模型时，也要让 Mock 依据 Observation 选择下一动作，而不是伪造 Trace。

## 7. 下一步

获得可控运行环境后，按“固定模型 revision → CUDA 编码 → Qdrant 写入与回查 → provider JSON 协议 → 合成评测矩阵”顺序补运行证据；所有真实结果仍需与离线契约分开记录。
